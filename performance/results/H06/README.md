# H06 — scanner eligibility, bypass and replay diagnostics

The new `version(NPeggedScannerMetrics)` diagnostic build instruments parser execution
to record scanner eligibility, scan attempts, outcomes, and replays at runtime.
Caller-owned fixed-capacity `ScannerReport` rows aggregate per-rule and per-region events
without heap allocation in hot paths. Totals remain complete and accurate even if the
number of distinct rule rows exceeds caller-provided capacity. Ordinary generated bytes
and parser semantics remain strictly unchanged when diagnostics are inactive.

```d
import npegged.peg;
ParseContext context;
ScannerStats[16] storage;
ScannerReport report;
report.rows = storage[];
context.scannerReport = &report;

auto result = check!(MyGrammar.Root)(context, input);
// report.total and report.rows contain exact call, scan, and replay counts
```

Static rule metadata (`scannerRuleNames`, `scannerRegionCounts`, `scannerRootProven`)
exposes emitted DFA region counts and root regularity proofs at compile time.

## Profile Findings & Hotspot Analysis

The profile collected 41 static rules across `BenchPEG`, `JSON`, and `BenchCSV`, and
evaluated 1,352 event rows across four cohorts:
- `combinators-selective`
- `combinators-full`
- `direct-selective`
- `direct-full`

Across all profiled workloads, 96 hotspot records were identified (records exhibiting
replays or fallback `originalCalls` in `check` or `records` modes).

### Reason Distribution

| Reason | Count | Description |
|---|---:|---|
| `failureDiagnostic` | 2,220 | DFA rejected input; replayed `Original` to obtain failure diagnostics and `failEnd` |
| `none` | 928 | Direct scan success or non-replayed terminal outcomes |
| `innerRecords` | 8 | Lowering skipped DFA due to nested record extraction requirements |
| `recordLowering` | 8 | Direct record lowering bypass |
| `budgetEdge` | 4 | Step or position budget edge encountered at token boundary |

### Key Architectural Insights for H07

1. **`failureDiagnostic` replay dominates all other fallback causes:** Over 98% of all
   replays are triggered because a regular token DFA scan failed, and `dfaToken`
   replayed the combinator `Original` expression simply to compute exact `failEnd`
   diagnostics or step progression.
2. **`BenchPEG.Sp/_dfa_Sp_1` is the single largest hotspot:** 1,820 replays occurred on
   optional whitespace checks where no whitespace was present in the input. The DFA scan
   fails at position 0, but because the combinator fallback was invoked, the parser re-ran
   the full Sp combinator hierarchy.
3. **No runtime semantics or speed changes in H06:** H06 is diagnostic-only. It proves
   that optimizing the exact failed-scan path in `dfaToken` (H07) has the potential to
   eliminate thousands of redundant combinator replays across real grammars.
